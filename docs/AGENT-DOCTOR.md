# Агент-доктор: контроль и восстановление других агентов

Эта схема добавляет отдельного технического агента, который проверяет Hermes-профили, распознаёт подтверждённый сбой, адресно перезапускает разрешённый gateway и сообщает результат владельцу.

## Что важно понимать

Один LLM-агент не должен быть единственным механизмом надёжности. Падение процесса лучше всего восстанавливает service manager (`systemd`, `launchd` или s6 в официальном Docker-образе). Доктор нужен для случаев, когда процесс активен, но канал не отвечает, проверки не проходят или ошибки повторяются.

Доктор на том же gateway не заметит падение этого gateway: вместе с ним остановятся агент и встроенное расписание. Поэтому основной автоматический запуск обеспечивает service manager, а для критичного бизнеса внешний мониторинг дополнительно проверяет VPS или Telegram-бота извне.

## Схема

```text
service manager ── автоматически возвращает упавшие процессы
       |
       +── основной gateway / профили бизнеса
       +── отдельный профиль doctor

doctor каждые 5 минут
  → список gateway
  → глубокий статус и hermes doctor
  → повторная проверка подозрительного состояния
  → один адресный restart
  → техническая + функциональная проверка
  → отчёт или эскалация
```

## 1. Подготовить реестр

1. Скопируйте `config/doctor-inventory.example.yaml` в закрытую рабочую папку клиента.
2. Внесите только реальные профили из `hermes profile list` и `hermes gateway list`.
3. Для каждого профиля назначьте владельца и решите, разрешён ли автоматический перезапуск.
4. Укажите безопасную функциональную пробу: например, тестовый запрос без записи в CRM, отправки клиентам и других внешних последствий.
5. Не добавляйте в реестр токены, пароли и содержимое `.env`.

Сначала установите `auto_restart: false` и проведите несколько циклов только в режиме наблюдения.

## 2. Создать отдельный профиль Доктора

Создайте профиль актуальной командой Hermes и скопируйте в него:

- `profiles/doctor/SOUL.md`;
- `profiles/doctor/AGENTS.md`;
- `skills/agent-fleet-doctor/`.

Для профиля задайте отдельный Telegram-бот или отдельный служебный канал, доступный только владельцу и техническому ответственному. Не выдавайте Доктору доступ к CRM, почте, платежам и клиентским документам: они не нужны для контроля gateway.

После установки проверьте:

```bash
hermes -p doctor doctor
hermes -p doctor gateway status --deep
```

## 3. Определить режим gateway

### Отдельные gateway-процессы

Проверка всех профилей:

```bash
hermes gateway list
hermes -p sales gateway status --deep
hermes -p sales doctor
```

Разрешённое восстановление только одного профиля:

```bash
hermes -p sales gateway restart
```

Имя `sales` — пример. Используйте только профиль из реестра. Для профиля `default` команды выполняются без `-p default`.

### Profile multiplexer

Если включён `gateway.multiplex_profiles`, вторичные профили обслуживает один основной gateway. Их нельзя поднимать отдельными gateway-командами. Доктор проверяет симптомы по профилям, но при подтверждённой общей аварии перезапускает только основной gateway:

```bash
hermes gateway restart
```

Это действие влияет сразу на все каналы и поэтому должно быть отдельно разрешено в реестре.

## 4. Выбрать границу прав

### Пользовательские службы

Если gateway установлены как user services под тем же техническим пользователем, адресные команды Hermes могут работать без `sudo`. На headless Linux убедитесь, что служба переживает выход пользователя; `gateway status --deep` показывает подсказку по systemd linger.

### Системные службы

Если текущий агент установлен с `--system`, не передавайте LLM общий пароль или неограниченный `sudo`. Сам systemd уже должен перезапускать процесс после падения. Для автоматического адресного восстановления администратор может создать отдельного Unix-пользователя и точечное правило `sudoers`, разрешающее только `is-active` и `restart` конкретных заранее известных unit-файлов. Имя каждого unit сначала проверяется вручную. Wildcard, shell, редактор, `sudo bash` и доступ ко всему `systemctl` запрещены.

До настройки такого правила Доктор только диагностирует системную службу и вызывает человека.

## 5. Политика состояния

| Состояние | Условие | Действие |
|---|---|---|
| `HEALTHY` | статус и функциональная проба успешны | записать результат |
| `DEGRADED` | единичный тайм-аут или предупреждение | повторить проверку, не перезапускать |
| `DOWN` | служба остановлена на двух проверках | адресный restart, если разрешён |
| `STUCK` | служба активна, но две проверки и проба неуспешны | сохранить диагностику и адресно перезапустить |
| `RECOVERING` | restart выполнен, идёт контроль | не запускать второй restart |
| `QUARANTINED` | две попытки за 30 минут не помогли | остановить автоматику и вызвать человека |

Рекомендуемый старт: проверка каждые 5 минут, подтверждение через 60 секунд, пауза после restart 120 секунд, максимум две попытки за 30 минут. Для долгих задач клиента интервалы нужно увеличить.

## 6. Плановый запуск

Hermes поддерживает cron-задачи и привязку скилла к отдельному профилю. Для наблюдения можно создать задачу, которая каждые пять минут запускает профиль `doctor` со скиллом `agent-fleet-doctor`. Сначала создавайте её без права перезапуска и проверьте вывод командой:

```bash
hermes cron list
hermes cron status
```

Расписание встроенного cron выполняет gateway. Поэтому оно не заменяет systemd и внешний uptime-monitor. Для простой детерминированной проверки без рассуждений и расхода токенов используйте script-only/no-agent cron, а модель подключайте только для разбора инцидента.

Не ставьте unattended-режиму общее разрешение на опасные команды. Изменения production должны проходить через точечную, заранее проверенную команду восстановления.

## 7. Проверка перед production

Проведите тесты на тестовом профиле:

1. Все профили здоровы — Доктор ничего не перезапускает.
2. Один тест статуса дал тайм-аут — Доктор ждёт повторного подтверждения.
3. Тестовый gateway остановлен — Доктор восстанавливает только его.
4. Процесс активен, но функциональная проба не проходит — Доктор сохраняет диагностику и выполняет одну попытку.
5. Два восстановления не помогли — профиль получает `QUARANTINED`, владелец получает сообщение.
6. Профиль не внесён в реестр — Доктор не меняет его.
7. В журнале встречается токен — в отчёте он скрыт.
8. Включён multiplexer — Доктор не запускает gateway вторичного профиля.
9. Доктор остановлен — service manager возвращает его без участия самого Доктора.

## 8. Шаблон сообщения владельцу

```text
ИНЦИДЕНТ АГЕНТА
Время: 2026-08-31 14:05 Europe/Moscow
Агент: sales / профиль sales
Состояние: STUCK → HEALTHY
Влияние: Telegram не отвечал около 7 минут
Подтверждение: две неуспешные проверки, служба была active
Действие: один адресный штатный restart
Проверка: deep status, doctor и тестовый запрос успешны
Попытки: 1 из 2 за 30 минут
Следующий шаг: наблюдение 30 минут
Владелец: {{ИМЯ}}
```

Если функция не восстановлена, так и напишите; не заменяйте это фразой «сервис запущен».
